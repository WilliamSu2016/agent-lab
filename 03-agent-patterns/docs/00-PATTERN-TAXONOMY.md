# Agent Architecture Patterns：分类、控制流与选型

本文依据 Anthropic 官方文章 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，聚焦架构，而非 OpenAI Agents SDK API。

阅读日期：2026-09-09。以下五种模式的定义、分类与典型适用场景来自原文；确定性边界、主要风险、不适用条件和 Research Agent 组合方案是基于原文的工程分析，不代表原文逐项给出的结论。

## 1. 先区分 Workflow 与 Agent

Anthropic 的核心区分是**谁控制完成任务的过程**：

| 类型 | 控制权 | 典型运行方式 |
|---|---|---|
| Workflow | 代码预先规定主要执行结构、阶段与转移规则 | 在固定链、固定候选分支或受约束循环中调用 LLM 和工具 |
| Agent | LLM 根据任务和环境反馈动态决定过程与工具使用 | 观察结果、决定下一步、执行工具、更新计划，直到完成或触及限制 |

**本文研究的五种模式在原文中全部属于 Workflow。** Orchestrator-Workers 的动态分解、Evaluator-Optimizer 的反馈循环具有更强的动态性，但原文没有因此把它们直接归类为自主 Agent。

判断架构时，不要把以下概念混为一谈：

- 使用名为 `Agent` 的 SDK 对象，不等于架构上就是自主 Agent。
- 多个 LLM、工具调用、条件分支或循环，本身都不能证明系统是 Agent。
- Workflow 可以包含模型决策；“预定义路径”不意味着每次执行的输出、分支和调用次数完全相同。
- Agent 仍然需要代码约束：工具权限、预算、超时、最大轮数和人工审批不应交给模型自由解除。

### 本文中 deterministic 的含义

这里的 deterministic 指：**给定相同输入和状态，程序按明确规则执行同样的调度、检查或转移**，不是指整个系统的答案可重复。

例如，程序执行 `score >= threshold` 是确定性比较，但如果 `score` 来自 LLM，质量判断仍由模型参与。搜索工具的调用与结果解析可以由代码控制，但外部搜索结果不保证稳定。即使设置较低温度，也不应把 LLM 输出视作严格确定性的结果。

后文用 `[D]` 表示程序规则，用 `[L]` 表示模型生成或判断，用 `[E]` 表示外部环境反馈。

## 2. 五种模式总览

| Pattern | 解决的核心问题 | 控制流骨架 | LLM 的主要决策 | 原文分类 |
|---|---|---|---|---|
| Prompt Chaining | 单次调用难以可靠完成可固定拆分的多步任务 | A -> 检查 -> B -> C | 每一步生成什么内容 | Workflow |
| Routing | 不同类型输入需要不同处理方式 | 分类 -> 选择既定分支 -> 专用处理 | 使用 LLM 分类时，决定类别 | Workflow |
| Parallelization | 独立工作需要加速，或同一任务需要多视角判断 | 分发 -> 并行执行 -> 聚合 | 子任务答案或各自判断 | Workflow |
| Orchestrator-Workers | 无法事先确定具体子任务 | 动态分解 -> 委派 -> 汇总 | 拆成哪些任务、如何分工与综合 | Workflow |
| Evaluator-Optimizer | 初稿不足，需要反馈驱动的改进 | 生成 -> 评价 -> 修改 -> 再评价 | 质量、缺陷、改进方式 | Workflow |

这些模式可以组合，不是互斥选项，也不是必须依次升级的成熟度阶梯。

## 3. Prompt Chaining

### 解决什么问题

把复杂任务拆成**事先已知、顺序固定、前后依赖清楚**的子任务，降低每次 LLM 调用的难度。例如先生成提纲，检查提纲，再写正文；或先写营销文案，再翻译。

### 控制流

```text
输入
  -> [L] A：生成中间结果
  -> [D] Gate：检查明确约束
       -> 不通过：[D] 按既定策略停止、报错或进入有限重试
       -> 通过：[L] B：基于 A 的输出继续处理
  -> [L] C：生成最终结果
  -> 输出
```

Gate 是可选的。上图的失败处理是实现时需要明确的策略，不是原文强制要求的固定方案。

### 哪些步骤是 deterministic，哪些由 LLM 决定

| 程序确定的部分 | LLM 决定的部分 |
|---|---|
| 步骤顺序、输入输出传递、必经阶段 | 提纲、草稿、翻译或摘要的具体内容 |
| 字段存在性、长度、格式等可编程 Gate | 若增加语义评价调用，是否符合语义质量要求 |
| 失败分支、重试上限、超时 | 按反馈修改内容，但通常不能自行跳过或添加阶段 |

如果 Gate 依赖“论证是否充分”等模型判断，就不再是纯确定性检查；程序只是按模型判断执行固定分支。

### 优势

任务职责清晰，中间产物可检查，便于定位错误；专注的小任务通常比一次性完成所有要求更可靠。

### 主要缺点

串行调用增加延迟；早期错误可能传递并放大；中间表示可能丢失信息；固定步骤难以适应不同任务。

### 不应该使用的情况

单次调用已经足够；无法稳定拆分步骤；子任务实际可以独立并行；或者任务必须依据新发现不断改变研究方向。

### 与 Agent 的边界

模型生成中间内容不意味着模型拥有过程控制权。如果模型开始根据结果自行增删步骤、选择工具并重规划，系统就超出了固定 Prompt Chaining，开始接近 Agent。

## 4. Routing

### 解决什么问题

把输入交给适合它的专用处理流程，避免一个通用提示词兼顾互相冲突的需求。例如把客服请求分为退款、技术支持和一般咨询，或把简单问题交给低成本模型、复杂问题交给能力更强的模型。

### 控制流

```text
输入
  -> [D 或 L] 分类器
  -> [D] 校验类别并映射到既定处理器
       -> 路由 A：专用流程 / 模型 / 工具
       -> 路由 B：专用流程 / 模型 / 工具
       -> 路由 C：专用流程 / 模型 / 工具
  -> 所选流程的结果
```

典型 Routing 选择一个分支。也可以设计多标签路由，但必须明确是否执行多个分支、如何聚合，不能把这些当作自动具备的能力。

### 哪些步骤是 deterministic，哪些由 LLM 决定

| 程序确定的部分 | LLM 决定的部分 |
|---|---|
| 候选类别、处理器集合、类别到处理器的映射 | 使用 LLM 分类时，解释输入并选择类别 |
| 基于关键词或规则的分类；固定传统分类器的推理也可为确定性过程 | 各分支中的专业回答或推理 |
| 非法类别处理、人工接管策略、超时与预算 | 不应擅自创建未授权分支或扩大工具权限 |

原文明确指出，路由分类可以使用 LLM，也可以使用传统分类模型或算法，因此 Routing 不要求路由决策一定由 LLM 完成。

### 优势

分离职责，能分别优化提示词、工具和模型；有机会同时改善专业性和成本；每类请求可以有不同的权限策略。

### 主要缺点

误分类会把后续处理带到错误方向；类别交叉或含糊时不稳定；路由器增加额外开销；多个专用分支需要维护。

### 不应该使用的情况

输入无法可靠分类；不同类别实际使用相同处理方式；一个请求必须综合多个领域，而设计只允许单选；分类成本超过专业化带来的收益。

### 与 Agent 的边界

从固定菜单里选一个分支仍是 Workflow。若模型在多轮执行中根据工具反馈连续决定下一项行动、切换目标并重规划，才逐渐接近 Agent，而不只是一次路由。

## 5. Parallelization

### 解决什么问题

原文区分两种形式：

| 形式 | 目标 | 例子 |
|---|---|---|
| Sectioning | 把可独立完成的工作并行执行，提高速度或关注度 | 对同一答案分别评价事实性、风格和完整性 |
| Voting | 对同一任务进行多次尝试，聚合不同判断以提高可信度 | 多个审查调用分别判断问题是否存在 |

### 控制流

```text
输入
  -> [D] 按预定义拆分规则或采样方案分发
       +-> [L] 子任务 / 尝试 1 --+
       +-> [L] 子任务 / 尝试 2 --+-> [D] 聚合 -> 输出
       +-> [L] 子任务 / 尝试 N --+
```

聚合可以是计票、阈值判断或结构化合并。如果还需要 LLM 写综合结论，则在聚合后增加 `[L]` 综合步骤；这属于组合设计，不是确定性聚合。

### 哪些步骤是 deterministic，哪些由 LLM 决定

| 程序确定的部分 | LLM 决定的部分 |
|---|---|
| 预定义拆分策略、调用数量规则、提示词配置 | 每个子任务的内容、各次尝试的答案或判断 |
| 并发上限、等待条件、失败处理 | 若增加综合调用，如何解释冲突并组织结论 |
| 多数票、阈值、去重规则、结果排序 | 通常不负责动态发明新的任务分工 |

“预定义”指分工规则已知，不要求输入条目数或调用数量永远固定。并发完成顺序也可能变化，应明确稳定排序与聚合方式。

### 优势

独立任务并行可降低总延迟；分工让每次调用更专注；多视角尝试有助于发现遗漏或不一致。

### 主要缺点

增加调用量、成本和限流压力；受最慢分支拖累；聚合冲突比较困难。多个调用可能共享同一偏差，**多数票不是事实证明**，重复调用也不保证错误相互独立。

### 不应该使用的情况

子任务存在强顺序依赖；任务必须共享实时可变状态；成本或并发配额不足；多个调用缺少有效多样性；或者无法定义有意义的聚合规则。

### 与 Agent 的边界

多个 worker 并不自动构成多 Agent 系统。预先定义分工并收集结果仍是 Workflow。若模型动态决定该研究哪些方向，就更接近 Orchestrator-Workers；若还持续依据环境反馈重规划，则更接近 Agent。

## 6. Orchestrator-Workers

### 解决什么问题

处理**事先无法预测具体子任务及其数量**的复杂任务。中央 LLM 根据当前请求生成分工，委派给 worker，再综合结果。

原文例子包括涉及多个文件的复杂代码修改，以及从多个来源收集和分析相关信息的搜索任务。

### 控制流

```text
输入
  -> [L] Orchestrator：分解任务、定义 worker 目标
  -> [D] 校验任务描述、权限、数量与预算
  -> [D] 调度 workers（独立任务可并行，有依赖的任务需排序）
       +-> [L] Worker A：完成被分配的任务 --+
       +-> [L] Worker B：完成被分配的任务 --+-> [L] 综合结果
       +-> [L] Worker N：完成被分配的任务 --+
  -> 输出
```

动态分解是核心，不是必须并行。校验和资源限制是工程上建议增加的约束。根据结果继续委派也可以加入，但不是这个基本模式必然具备的行为。

### 哪些步骤是 deterministic，哪些由 LLM 决定

| 程序确定的部分 | LLM 决定的部分 |
|---|---|
| 任务结构校验、可用 worker / 工具范围、权限 | 根据具体请求决定子任务数量、内容和分工 |
| 执行委派、并发限制、依赖调度、超时与预算 | worker 的推理和输出；在授权范围内提出工具请求 |
| 结果收集、终止上限、错误显式上报 | 综合各 worker 结果，处理相关性、冲突和遗漏 |

关键区分：**程序负责可靠地执行分工，模型负责提出分工。**

### 优势

适应不同任务的规模和结构；能够按需拆解复杂问题；可让 worker 专注不同资料或领域，并利用独立子任务的并行性。

### 主要缺点

错误分解会影响全部 worker；容易重复劳动或遗漏跨任务信息；委派、上下文传递和综合增加成本；协调者可能成为瓶颈；执行轨迹较难预测和复现。

### 不应该使用的情况

任务拆分早已固定，简单并行足够；任务很小；子任务高度耦合且拆分会丢失关键上下文；模型无法可靠规划；预算不支持协调开销。

### 与 Agent 的边界

这是五种模式中**过程规划明显由 LLM 参与**的一种，但原文仍称其为 Workflow。若外层结构始终是“分解一次 -> 执行 -> 汇总”，自治程度仍受明显限制。

当协调者能根据真实工具结果持续重规划、增删任务、自主选择下一步工具并判断何时结束时，就接近原文所描述的 Agent。worker 自身也可能是 Agent，因此需要分别判断外层编排和 worker 内部控制流。

## 7. Evaluator-Optimizer

### 解决什么问题

通过明确的评价标准和可操作反馈，让候选结果迭代改进，而不是期待一次生成就达到要求。

原文给出两个重要适配信号：人类反馈能够显著改善结果；LLM 也能提供类似的有效反馈。原文例子包括精细文学翻译，以及需要多轮搜索与分析的复杂搜索任务。

### 控制流

```text
输入
  -> [L] Generator / Optimizer：生成候选结果
  -> [L] Evaluator：依据明确标准评价并给出反馈
  -> [D] 检查评价结果与停止规则
       -> 达标：输出
       -> 未达标且预算允许：
            [L] Optimizer 根据反馈修改 -> 返回评价步骤
       -> 达到轮数 / 成本 / 时间上限：
            显式返回未达标状态、保留结果或转人工
```

Evaluator 和 Optimizer 是两个职责，不要求使用两个不同的基础模型。可以补充程序化评价，但原文模式的核心是一轮生成调用与另一轮评价调用形成反馈循环。

### 哪些步骤是 deterministic，哪些由 LLM 决定

| 程序确定的部分 | LLM 决定的部分 |
|---|---|
| 生成与评价交替的结构、反馈传递方式 | 候选答案、质量评价、具体缺陷与改进建议 |
| 最大轮数、成本上限、超时、阈值比较 | 如何根据反馈修改；复杂搜索中是否需要更多证据 |
| 格式约束、引用字段存在性等机械检查 | 语义是否完整、论证是否成立等非机械判断 |

程序执行停止规则，不代表“达标”就是客观事实。如果依据模型的 `pass` 或分数停止，模型仍参与质量判断。到达预算上限也不等于任务已经成功。

### 优势

显式暴露质量问题；适合初稿容易产生但打磨困难的任务；可以把反馈聚焦到具体缺陷，而不是无方向地重新生成。

### 主要缺点

循环增加延迟和成本；评价者可能误判或与生成者共享盲点；修改不保证单调改善；可能反复震荡或迎合评价标准，却没有提高真实质量。

### 不应该使用的情况

没有清晰标准；评价者无法可靠识别优劣；反馈不能转化为有效修改；需要极低延迟；缺失的是外部证据，却只允许模型反复改写同一份内容。

### 与 Agent 的边界

固定的“生成 -> 评价 -> 修改”循环仍是 Workflow，迭代次数可变也不改变这一点。当反馈驱动模型自主选择新搜索、切换工具、重新分解问题和调整整体计划时，系统才开始超出固定优化循环，接近 Agent。

## 8. 哪些地方开始接近 Agent？

判断依据不是 LLM 数量，而是**模型对执行过程拥有多大范围的决策权**。

| 情况 | 架构判断 |
|---|---|
| 模型按顺序写提纲、正文和摘要 | 固定链式 Workflow |
| 模型从既定类别中选择一个处理器 | Routing Workflow |
| 多个模型并行处理固定分工 | Parallelization Workflow |
| 模型决定这次需要哪些子任务 | Orchestrator-Workers Workflow，具有动态规划能力 |
| 模型评价是否继续修改同一结果 | Evaluator-Optimizer Workflow，具有反馈决策能力 |
| 模型观察搜索或执行结果，决定下一步行动、工具、任务分解和完成时机 | 接近或属于 Agent |

一个典型 Agent 的控制流是：

```text
目标
  -> [L] 决定下一步行动
  -> [D] 校验权限与预算，并执行获准工具
  -> [E] 工具结果 / 外部环境反馈
  -> [L] 更新理解与计划
  -> 继续行动、请求人工判断，或完成
```

环境反馈很重要：原文强调从工具调用结果、代码执行等渠道获得真实反馈。只有模型对自己答案的反复评论，并不能替代外部证据。

Workflow 与 Agent 可以嵌套。外层 Workflow 可以调用一个自主搜索 Agent；Agent 也可以把固定的数据清洗链作为工具。分类应明确讨论的是哪一层。

## 9. 哪种 Pattern 最适合 Research Agent？

### 结论

**若研究任务是开放式、多来源、子问题无法预先列全，五种模式中最适合作为主干的是 Orchestrator-Workers；若还要求迭代补证，适合组合 Evaluator-Optimizer。**

这是基于任务特征的选型建议，不是原文给出的统一排名。依据是原文明确把多来源搜索列为 Orchestrator-Workers 的适用场景，把需要多轮搜索和分析的复杂搜索列为 Evaluator-Optimizer 的适用场景。

### 为什么选择 Orchestrator-Workers

研究问题常需要临时确定子问题、来源类型与研究深度。比如“比较两种技术方案是否适合某个业务”，实际分工可能涉及功能、成本、限制、证据时效性和相互矛盾的材料，而不是每次都查同样的几个栏目。

动态协调者负责确定调查范围；workers 聚焦不同子问题并提交证据；协调者综合答案。相比固定分工，这更适合输入差异大、研究路径不确定的任务。

### 推荐组合

```text
研究问题
  -> [L] Orchestrator：分解子问题、明确证据需求
  -> [D] 校验任务、工具权限、来源策略与预算
  -> Workers：对独立子问题并行搜索和分析
       [L] 生成查询 / 请求工具
       [D] 执行获准调用
       [E] 返回资料
       [L] 提取论点、证据、来源和不确定性
  -> [L] 综合研究草稿
  -> [L] Evaluator：检查覆盖度、证据支持、冲突与时效性
  -> [D] 执行继续 / 终止规则
       -> 证据充分：输出带来源的结论
       -> 存在缺口且预算允许：补充研究并重新综合
       -> 预算耗尽：输出已有发现，并明确未解决问题
```

上述组合中，Parallelization 负责独立研究工作的并发；Evaluator-Optimizer 负责发现缺口并驱动改进；Prompt Chaining 可以用于固定的“证据整理 -> 草稿 -> 格式化”；Routing 仅在确实存在不同研究类型或成本层级时加入。

如果补充研究只能进入预先限定的分支，整体仍可视为组合 Workflow。如果协调者根据新资料自主改变研究路径、选择工具和决定后续行动，整体就更接近真正的 Research Agent。

### Research Agent 的关键约束

- **评价证据而不只是文风**：判断关键结论是否获得来源支持、是否存在反例或冲突、信息是否过时。
- **让发现可追溯**：worker 返回来源、相关证据及其支持的论点，而不只是没有出处的摘要。
- **区分机械检查和语义判断**：程序可检查来源字段是否存在，但来源是否真的支持结论，需要进一步判断；模型的自信分数不能充当证明。
- **控制研究范围和成本**：限制调用数、并发数、时间与补证轮数；停止时明确区分成功完成、预算耗尽和工具失败。
- **不要把多来源等同于独立证据**：多个页面可能转载同一消息，多 worker 的一致结论也可能来自相同错误来源。

这些是组合架构的工程建议，不是要求每个研究任务都配齐所有组件。

### 哪些研究任务不需要这套组合

| 研究任务特征 | 更简单的起点 |
|---|---|
| 单一事实查询、来源明确 | 检索加单次 LLM 回答，甚至直接返回查询结果 |
| 固定报告模板、固定处理阶段 | Prompt Chaining |
| 固定几个独立维度或资料集合 | Parallelization |
| 主要差异在请求类型，如文献检索与内部知识查询 | Routing |
| 已有足够材料，重点是依据明确标准改进报告 | Evaluator-Optimizer |
| 子问题随请求变化，需要动态分工 | Orchestrator-Workers |
| 新证据不断改变方向，需要自主决定下一步行动 | 带工具和环境反馈的 Agent，可组合上述 Workflow |

最合适的学习顺序是先识别控制权与数据依赖，再选择最简单的结构；不要因为项目使用 OpenAI Agents SDK，就默认需要自主循环或多个 Agent。
