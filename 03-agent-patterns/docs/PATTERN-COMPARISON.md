# 五种 Agent Patterns：比较与选型

本文基于 Anthropic 官方文章 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)，结合本项目的五种实现。重点是架构选择，而不是 OpenAI Agents SDK API。

**先选最简单的可用方案，再为明确的瓶颈增加模式；不要为了“像 Agent”而组合所有模式。**

## 总览

表中的“动态”指分支、任务分解或迭代次数会不会随输入和运行结果变化，不是指模型每次生成的文本不同。“是否需要多个 Agent”区分逻辑角色与 SDK 对象：多个 LLM 调用不要求多个不同模型，也不必构成多个自主 Agent。

| Pattern | 控制流由谁决定 | 是否动态 | 是否并行 | 是否需要多个 Agent | 适合什么任务 | 主要缺点 |
| -------------------- | ------- | ---- | ---- | ------------ | ------ | ---- |
| Prompt Chaining | 程序固定步骤、顺序和检查点；LLM 生成每步内容 | 流程通常固定，内容动态 | 链上有依赖的步骤不并行 | 模式不要求；本项目用 4 个独立 Agent | 可预先拆解的研究、文档生成、抽取后转换 | 串行延迟、上游错误传播、中间信息丢失、流程僵化 |
| Routing | 分类器决定类别，程序映射到预定义路径；本项目分类器是 LLM | 动态选择已有分支，不创造新流程 | 本项目不并行，只执行一个 Specialist | 模式不要求；本项目每次运行 Router + 1 个 Specialist | 不同意图、领域、难度需要不同处理的任务 | 误分类、跨类别问题覆盖不足、分类调用与维护开销 |
| Parallelization | 程序决定拆分规则、并发调度和汇合；LLM 完成独立任务 | 不要求 LLM 动态规划；任务数也可以由输入和程序规则确定 | 是，独立调用并发 | 不要求；同一模型可多次独立调用；本项目是 3 个 Researcher + Synthesizer | 独立对象比较、多角度审阅、多次采样投票 | 总调用成本、限流、等待最慢分支、结果冲突与汇总损失 |
| Orchestrator-Workers | LLM 决定任务内容和数量；程序校验、限额、派发、汇合 | 是，运行时动态分解子任务 | 可并行也可串行；本项目 Workers 并发 | 需要协调与执行的逻辑角色，不要求不同模型；本项目另设 Synthesizer | 开放式研究、范围未知的跨文件代码修改 | 错误分解、重复研究、协调开销、任务扩张与资源风险 |
| Evaluator-Optimizer | 程序定义生成—评价循环及退出规则；LLM 的评价影响实际轮数和修订内容 | 是，反馈与实际轮数动态，循环骨架固定 | 同一产物的各轮不能直接并行；多评价者可另行并发 | 需要生成与评价两种逻辑角色；本项目用 2 个独立 Agent | 可根据明确反馈改进的报告、翻译、代码修订 | 串行重写成本、评分偏差、质量不收敛、迎合评分而非真实需求 |

Anthropic 将这五种都列为 **Workflow**。Workflow 可以包含条件分支、动态任务列表和有界循环；“预定义代码路径”不等于“每次执行轨迹完全相同”。

本项目的 `Agent` 是 SDK 的角色配置对象。使用了这个类、工具调用或多个角色，都不能单独证明系统是 Autonomous Agent。

## 1. Prompt Chaining 与 Agent 的边界在哪里？

**边界在于：模型只填写预定步骤的内容，还是能够根据环境反馈决定后续行动。**

本项目的流程是：

```text
Planner -> Researcher -> Analyst -> Writer
```

Planner 可以生成不同研究维度，但不能决定删掉 Writer、增派几个 Researcher，或在分析后重新规划流程。这是固定链条中的内容生成。

如果系统能够根据检索结果自主判断“缺少原始证据，需要换查询、读取资料、重新分析，再决定下一步”，就开始具备 Agent Loop 的特征。要按层次判断：Researcher 内部可能存在模型驱动的工具循环，但外层四步流程依然是 Prompt Chaining。

**有上限不代表不是 Agent，没有上限也不代表更自主。** 自主 Agent 同样应有预算、最大步数、权限和人工检查点。自主程度看行动决策权，不看有没有 `for` 循环或是否使用 Handoff。

## 2. Routing 为什么不是简单 if/else？

需要拆开看两件事：**分类决策**与**执行分支**。

本项目先让 LLM 理解自然语言意图，输出 `technical`、`business` 或 `general`；然后程序用固定字典选择 Specialist。后半段完全可以写成 `if/else`，并不神秘。

真正的架构价值是“将输入交给适合它的专门处理流程”：不同提示词、工具、权限、模型或服务策略可以独立维护。LLM 分类比简单关键词匹配更能处理同义表达和上下文，但也会误判。

**Routing 不强制使用 LLM。** 官方文章明确允许传统分类模型或算法。如果工单已经有可信的类别字段，或规则足够准确，直接 `if/else` 就是合理且更便宜的 Routing。不要为了这个模式额外调用一次模型。

## 3. Parallelization 为什么不等于 Multi-Agent？

两者描述不同维度：**Parallelization 是执行时序，Multi-Agent 是角色组织。**

同一个模型可以并发完成三次独立摘要，或对同一问题多次采样再投票，不需要为每次调用设计一个自主 Agent。反过来，本项目 Prompt Chaining 的四个角色都按顺序执行：多个 Agent 不意味着并行。

官方文章包含两种 Parallelization：Sectioning 将不同独立子任务同时执行；Voting 对同一任务多次执行并聚合。本项目“三种语言分别研究”属于 Sectioning，不是这个模式的唯一形态。

另外，**固定的是拆分逻辑，不一定是任务数**。程序按用户提供的文档列表一文档一任务，数量随输入变化，也不自动变成 Orchestrator-Workers；关键仍是有没有 LLM 动态决定如何分解任务。

## 4. Orchestrator-Workers 为什么比 Parallelization 更动态？

Parallelization 通常已知道任务怎么拆，只需决定怎么同时执行；Orchestrator-Workers 连“需要研究哪些问题、分成多少项”也交给 LLM 根据输入判断。

| 本项目示例 | 分解依据 |
| --- | --- |
| Parallelization | 程序预先指定 Python、TypeScript、Go |
| Orchestrator-Workers | Orchestrator 从问题生成结构化 `ResearchPlan.tasks`，程序执行数量检查 |

例如“全面分析 AI Agent 技术栈”可以拆为模型、运行时、基础设施、治理等角度；换成“选择客服知识检索方案”则应产生不同任务，而不是重复同一清单。

这里不仅是内容变化：被派发的任务数量和职责也随计划变化，因此 **LLM 对执行结构有受限的影响**。但本项目仍只有一次规划、一次派发与一次综合，不会根据 Worker 结果持续重规划。`MAX_WORKERS = 5` 在派发前由程序检查。

动态任务不天然独立。如果任务 B 依赖 A 的结果，就必须按依赖顺序执行，不能因为它们都是 Workers 就直接并行。

## 5. Evaluator-Optimizer 为什么需要明确 Evaluation Criteria？

**没有明确标准，反馈循环就可能成为反复改写，而不是可衡量的改进。**

“不够好”“再深入一点”既不可稳定打分，也不能指导具体修改。评价标准应在运行前确定，并与用户的成功条件一致：

| 标准 | 可执行的评价方式示例 |
| --- | --- |
| 回答用户问题 | 是否比较了指定对象，是否按用户约束给出推荐 |
| 覆盖主要维度 | 是否覆盖任务要求的运行时、可控性、部署、成本等维度 |
| 无明显事实错误 | 将重要能力声明与对应版本的原始资料核对；无法核实则标记不确定 |
| 证据充分 | 关键结论是否有可追溯且实际支持该结论的来源，而不只是列出 URL |
| 结构清晰 | 是否区分事实、判断、限制和建议，比较结构是否便于阅读 |
| 无重要遗漏 | 是否漏掉会改变选型结论的约束、风险或适用条件 |

本项目默认 `score >= 8` 停止，否则继续，最多 3 轮，返回历史最高分版本。这是**程序依据模型评分作出确定性判断**，不是独立于模型的客观质量裁决。`pass` 与分数不一致的记录、Pydantic 的范围校验，都不能证明评分本身正确。

已有运行文档记录了 **7 -> 7 -> 7**。这说明没有观察到评分改善，不能单凭反馈变多、报告变长就断言结果更好；并列时保留最早版本，也不保证它最简洁或最准确。

本项目 Evaluator 没有检索工具，仅看报告，无法独立验证所有事实。独立 Agent 角色也不等于独立知识来源。实际应用应结合来源核验、可执行检查和人工抽样；缺少证据时要补资料，而不是只润色。标准应包含评分锚点、可操作反馈及关键失败项，避免每轮不断追加新要求。

## 6. 哪些 Pattern 可以组合？

**五种模式都可组合，前提是各自解决不同且已经观察到的问题。** 以下是架构选项，不代表项目目前已经将这些模块接成一个系统。

| 组合 | 合理用途 | 需要控制的边界 |
| --- | --- | --- |
| Routing + Prompt Chaining | 不同客服意图进入各自固定处理流程 | 类别可可靠区分；不要让所有流程都运行 |
| Prompt Chaining + Parallelization | 先生成统一比较维度，再并发收集独立资料，最后分析写作 | 只有依赖已满足的阶段才能并发 |
| Parallelization + Evaluator-Optimizer | 多角度研究汇总后，对整份报告评价和修订 | 先汇总再评价整体；不要每次修订都无差别重跑全部研究 |
| Orchestrator-Workers + Parallelization | 动态生成任务后，并发执行独立 Workers | 验证依赖关系，限制任务数与并发数 |
| Orchestrator-Workers + Evaluator-Optimizer | 开放式研究后发现缺口，针对不足补研究和修订 | 统一总预算，避免每轮完整重新分解所有任务 |
| Routing + Evaluator-Optimizer | 只为高价值或高风险请求启动昂贵的修订流程 | 风险判定可靠；低延迟路径不应被强制多轮重写 |

外层流程可以确定性调度，内层某一步可以使用另一种模式。每增加一层，都应明确输入输出、失败处理、停止规则与成本责任。

## 7. 哪些 Pattern 不应该组合？

**没有永远不能组合的模式对；不应该组合的是职责重复、依赖冲突或预算失控的具体设计。**

| 不建议的组合方式 | 原因 | 更合适的处理 |
| --- | --- | --- |
| 把一条有数据依赖的 Prompt Chain 全部并行化 | 下游还没有上游结果 | 只并行同一依赖层的独立步骤 |
| Router 选择一个 Specialist 后，仍把所有 Specialist 全跑一遍 | 抵消了按需分流的收益 | 需要一个视角用 Routing；需要全部视角用 Parallelization |
| 对永远固定的任务先跑 Orchestrator，再照原清单并行 | 多了一次规划成本和不确定性 | 直接使用程序定义的 Parallelization |
| 每个 Worker 都跑完整修订循环，外层又反复重启全部 Workers | 工作量相乘，反馈还可能互相冲突 | 先设全局预算，再决定局部或整体评价 |
| 一个 Evaluator 要求更短，另一个无限要求更全面 | 缺少共同评分规则，容易来回振荡 | 在同一份标准中明确优先级和长度约束 |
| 将付款、退款、发信等副作用操作放入自动重试或修订循环 | 可能重复执行真实业务动作 | 修订计划或文本；执行动作另设幂等、权限和审批控制 |

简单任务不应因为“五种都学过了”就经过五种模式。一个效果足够好的单调用方案，通常比五层组合更值得上线。

## 8. 哪种 Pattern 最适合 Research Agent？

**开放式、研究范围无法提前确定时，首选 Orchestrator-Workers；初版 Solo 产品通常先用 Prompt Chaining。**

Research Agent 的任务差异很大。固定格式的技术选型报告可以用“维度 -> 搜索 -> 分析 -> 写作”；固定比较三种技术且需要提速，适合 Parallelization；任意开放问题，需要运行时决定研究角度，才体现 Orchestrator-Workers 的优势。

高质量深度研究可以再加有界 Evaluator-Optimizer，但评价必须能识别真实证据缺口并触发有效补充。已有项目记录中的空搜索结果和评分停滞提醒我们：**更多角色无法弥补检索数据缺失，更多修订不自动产生证据。**

## 9. 哪种 Pattern 最适合 Coding Agent？

**复杂、跨文件且范围未知的修改，Orchestrator-Workers 最适合任务组织；对一个补丁反复修正，Evaluator-Optimizer 最适合质量反馈。**

Anthropic 将跨文件代码修改列为 Orchestrator-Workers 的典型场景，因为文件数量和具体修改随需求变化。实际分工必须尊重代码依赖与文件所有权，不能让多个 Worker 同时随意改同一个文件。

代码还有报告不具备的优势：可以用已有测试、编译器、类型检查和运行结果提供外部反馈。评价不应只依赖 LLM 的“9 分”。测试通过也不等于全面正确，仍需检查需求覆盖和系统影响。

小范围修复通常不需要分派 Workers：单个带工具的 Agent，或者固定“定位 -> 修改 -> 运行检查”流程就足够。能自主根据错误重新定位、改动并再次执行的 Coding Agent，其外层可能已是 Agent Loop，而不只是五种 Workflow 中的一种。

## 10. 哪种 Pattern 最适合 Customer Support Agent？

**多数有清晰业务分类的客服入口，Routing 是最好的起点。**

知识问答、退款政策、技术排障、账户问题需要不同资料和处理权限，不应塞进一个越来越长的万能提示词。路由后，标准业务处理适合 Prompt Chaining。

但不是所有客服都适合单次分类：跨意图请求、复杂排障可能需要澄清、升级人工，或更灵活的工具循环。涉及退款、账户变更等动作，必须由业务代码验证授权与政策，不能以 LLM 的类别或评分代替审批。

低延迟客服通常不宜默认执行多轮 Evaluator-Optimizer；可在高价值、复杂工单上按需启用。

## 11. 哪种 Pattern 最容易造成成本爆炸？

**单模式中，Orchestrator-Workers 的动态任务扩张最值得警惕；组合中，动态分派再叠加多轮修订风险最高。** Evaluator-Optimizer 的反复长文本生成也可能更贵，实际金额取决于 token、模型价格、搜索和重试，不能只按模式名称绝对排序。

将“阶段运行”与“模型请求”区分开：一次 `Runner.run` 内可能含多次模型请求及工具调用。

| 本项目默认成功路径 | 阶段运行数量，不等于模型请求总数 |
| --- | --- |
| Prompt Chaining | 4 |
| Routing | 2：Router + 一个 Specialist |
| Parallelization | 4：三个 Researcher + Synthesizer |
| Orchestrator-Workers | `N + 2`，`1 <= N <= 5` |
| Evaluator-Optimizer | `2R`，默认 `1 <= R <= 3` |

若每轮都完整重跑一个含 N 个 Workers 的研究流程，再加一次评价，阶段数约为 `R * (N + 3)`；Worker 内部若再反复检索和重写，总开销继续放大。并行通常减少等待时间，不会自动减少 token 或工具费用。

应限制全局总任务数、总模型请求数、token/金额、工具调用、并发和重试，而不只限制每个局部循环。本项目 Orchestrator 的派发上限为 5；Evaluator 的 3 轮和 8 分是默认参数，调用方可覆盖，不应误读为不可突破的全局预算。

## 12. 哪种 Pattern 最容易造成 latency 增加？

**在单轮工作量相近时，Evaluator-Optimizer 最容易拉长端到端延迟，因为多轮生成与评价必须串行。** Prompt Chaining 也有明确的串行开销；很重的 Worker、长篇综合或限流可能使其他模式更慢，没有无条件排名。

用 `T` 表示一个阶段的耗时，含其内部模型与工具等待：

```text
Prompt Chaining:      T1 + T2 + T3 + T4
Routing:             T_router + T_selected_specialist
Parallelization:     max(T_worker_i) + T_synthesis
Orchestrator-Workers: T_plan + max(T_worker_i) + T_synthesis
Evaluator-Optimizer: sum(T_generate_i + T_evaluate_i), i = 1..R
```

并行公式假设独立任务、并发容量足够，并忽略调度开销；限流、排队、重试和慢分支都会改变实际结果。

项目 Parallelization 文档记录过研究阶段顺序约 **16.64 秒**、并发约 **5.81 秒**。这是单次不同调用的观察，不是稳定的性能保证，也不包含两种调度方式各自完整端到端报告的对比。上线选型应关注代表性负载下的端到端 P50/P95，而不只看一次最快结果。

## 如果我是一个 Solo Developer，我应该如何选择这五种 Pattern？

**先做能回答真实问题的最小系统；只在明确知道“哪里不够好”时，增加对应模式。** 五种模式不是从低到高必须依次升级的等级。

| 我观察到的问题 | 我的选择 | 暂时不做什么 |
| --- | --- | --- |
| 单次调用加必要检索已经足够 | 保持单调用或单个带工具的 Agent | 不为了架构展示拆成多个角色 |
| 一次调用同时承担太多职责，步骤却很稳定 | Prompt Chaining | 不引入动态规划 |
| 用户请求类别明确，不同类别需要不同处理 | Routing；能用规则就先用规则 | 不让所有 Specialist 都回答 |
| 已知独立任务顺序执行太慢 | Parallelization | 不并行有数据依赖或写入冲突的任务 |
| 输入多样，无法预先确定子任务范围 | 有数量和预算限制的 Orchestrator-Workers | 不递归、无限派发 Workers |
| 草稿已有价值，明确反馈能带来可衡量改进 | 有界 Evaluator-Optimizer | 不将“让模型满意”当成功标准 |

对这个 Research Agent 学习项目，我会保留五个独立示例作为对照，而不是立刻合并：

1. 先用 Prompt Chaining 交付一种固定研究报告，验证用户真正需要哪些内容。
2. 优先改善检索质量与来源可追溯性；证据不足时，增加角色不是解决办法。
3. 只有独立检索确实拖慢响应时才并行；只有分解规则确实无法预设时才加入 Orchestrator。
4. 用少量有代表性的真实问题比较质量、成本、端到端延迟和人工修改时间，不只比较 LLM 自评分。
5. 只有反馈可执行且改善可观察时才加修订循环；到达预算仍不达标就说明限制或转人工，不无限重试。

**我的默认选择：固定研究流程用 Prompt Chaining，客服入口用 Routing；并行是提速手段，Orchestrator 是应对未知分工的手段，Evaluator-Optimizer 是有证据支持时才启用的质量改进手段。**
